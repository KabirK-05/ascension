## The three rules that get PRs rejected

**1. No subtitle text. Anywhere.** No caption, helper, or explanatory sentence under a
title, number, or card header. No "Track your…", no "Here's your…", no motivational
copy. A label is a noun of at most two words. If a number needs a sentence, the label
is wrong — fix the label. `docs/DESIGN_RULES.md` §1 is the full list, and a reviewer
may reject your PR by citing a rule number alone.

**2. Never commit the `.xcodeproj`.** It is generated by `tuist generate` and
gitignored. A committed project file conflicts on every parallel merge and is why this
project uses Tuist at all.

**3. Never commit a secret.** API keys go in Keychain (app) or `wrangler secret`
(edge). No real health data in the repo, ever — `exports/` is gitignored.

## Branches

```
main      production only. PRs from `staging` only, titled `release: …`
staging   integration. The default branch. Your PR target.
asc/<id>-<slug>   your ticket branch, cut from `staging`
```

Cut from `staging`, never from `main`. Squash-merge into `staging`. `staging` is the
repo's default branch, so `gh pr create` targets it correctly without `--base`.

## Stay inside your ticket

One ticket, one branch, one package. **Do not edit another ticket's package** —
another session is probably in it right now. Module dependencies:

```
Features → DesignSystem, AscensionCore, AscensionEngines
AscensionCore, AscensionEngines → nothing
No feature imports another feature.
```

Blocked on a contract another ticket owns? **Stop and report.** Do not stub around it
and do not widen your scope to unblock yourself.

## Quality gates

- Engines (readiness, trends, calorie rules) are pure functions over value types and
  **may not merge untested**. The spec calls them the product (§8).
- CI must be green: SwiftLint, `swift test` on the pure packages, `tuist generate` +
  simulator build, `vitest` for `edge/`.
- Changed a field shape? Bump `schemaVersion` and update `docs/EXPORT_SCHEMA.md` in
  the same PR.
- Verify your work and report the command you ran and its real output. Never "should
  work".

## UI work specifically

Search **Mobbin MCP** for reference flows before building or restyling a screen (spec
§4) and note in your PR which references informed the layout. Patterns yes — layout,
hierarchy, density, interaction. Never brand assets, copy text, or proprietary icons.

Every UI PR: screenshots in light **and** dark mode, the one question the screen
answers, and what you removed.

## Hard product constraints

These come from the spec and are not yours to relax:

- **No workout recording.** The Apple Watch Workout app records. This app plans
  (WorkoutKit), reads (HealthKit), and interprets. Never a recorder or a live logger.
- **HealthKit is the source of truth** for workouts, HR, HRV, sleep, steps, energy,
  weight. Mirror what you need; never fork the truth.
- **Chicken and eggs are the only meats.** No pork, no beef, in any suggestion, seed,
  or sample data, ever. Milk + Bournvita is the one accepted dairy drink.
- **If a feature can't be exported, don't build it** (spec §3).
